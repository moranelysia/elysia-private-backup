# 爱莉希雅桌面陪伴 Agent：潜在问题与风险评估

更新日期：2026-10-09

## 1. 总体结论

### 当前自用阶段的优先级调整

短期只由开发者本人使用，因此代码签名、公开分发、陌生用户支持、角色资源再分发授权暂不作为近期阻断项；仍应避免把无权分发的资源上传或分享。当前最高优先级改为数据不丢失、API Key 安全、Shell 权限、提示注入、服务降级和开发时间控制。

开发投入按每周约 20 小时重新规划，近期 8–10 周可以集中完成安装、三模式、记忆和基础语音。GPT/Codex 额度不足通过 DeepSeek Harness分工解决，但任何 Agent生成的修改仍需通过同一测试和安全边界。

项目作为个人自用原型已经具备较完整的闭环，但距离公开安装包仍有四类核心风险：

1. **发布授权**：爱莉希雅角色设定、立绘、Live2D、动作、语音和克隆音色不能因为“程序免费”就默认允许再分发。
2. **系统权限**：工作模式能够运行 Shell，实际权限可能覆盖整台电脑，远大于文件工具的白名单。
3. **隐私与密钥**：长期记忆、聊天、麦克风、截图和社交消息会集中形成高敏感数据；API Key 也需要系统级安全存储。
4. **工程范围**：三种模式、语音、视觉、社交渠道、桌宠和 Agent 工具同时推进，对个人开发者的维护负担过大。

因此应先发布“安装 + 三模式 + 可控记忆”的本地基础版，再逐项增加外部能力。

## 2. 风险优先级

| 优先级 | 问题 | 当前状态 | 可能后果 | 建议 |
| --- | --- | --- | --- | --- |
| P0 | 角色、音色和 Live2D 分发授权 | 未形成发布清单 | 安装包无法公开分发、被要求下架 | 程序与角色包分离；公开版使用自有或明确授权资源 |
| P0 | Shell 权限过大 | 已有确认，但不是系统沙箱 | 误删文件、执行恶意命令、提示注入越权 | 工作目录隔离、命令预览、危险操作二次确认、低权限子进程 |
| P0 | API Key 与登录凭据 | 安装版尚未完成 | 密钥泄漏、账号被盗用和产生费用 | 使用 Electron `safeStorage`，日志脱敏，提供立即撤销入口 |
| P0 | 用户数据仍需迁到 `userData` | 已列入安装阶段 | 安装目录不可写、升级或卸载丢数据 | 安装包前完成数据目录迁移和版本化迁移脚本 |
| P0 | 提示注入通过网页、附件、社交消息进入工具层 | 现有权限只能缓解部分风险 | 外部文本诱导 Agent 读文件、运行命令或发送数据 | 外部内容标记为不可信；工具策略不听从内容中的“指令” |
| P1 | 外部服务不可用 | 语音、模型和桌宠均有外部依赖 | 启动慢、卡住、功能整体不可用 | 服务健康检查、超时、重试、熔断和文字降级 |
| P1 | 大文件与耦合 | `main.js`、`chat.js` 仍较大 | 每次修改容易引入回归 | 按窗口、IPC、附件、任务和服务适配器逐步拆分 |
| P1 | 缺少 Electron 真机端到端验证 | 本地核心测试通过，GUI 未完整验收 | 自动测试全绿但安装后无法使用 | 增加首次启动、对话、退出、重启、卸载冒烟测试 |
| P1 | 模型接口和名称变化 | 当前依赖云模型接口 | 模型下线后突然无法对话 | 模型适配层、可配置模型名、启动时能力探测 |
| P1 | 记忆错误与人格漂移 | 记忆规则已有基础 | 错记用户事实、关系突变、错误长期强化 | 记录来源、允许纠正、置信度和过期机制 |
| P1 | 社交平台规则与封号风险 | 尚未接入 | 账号限制、接口突然失效 | 优先官方接口；个人号非官方自动化不作为核心依赖 |
| P2 | 性能与资源占用 | Electron + 桌宠 + 本地语音 | 内存、显存、电量占用高 | 按需启动服务、空闲休眠、显示资源状态 |
| P2 | 单人维护与学业冲突 | 开发时间有限 | 半成品越来越多、长期无法发布 | 两周一个小版本；同一时间只做一个主功能 |

## 3. 成本问题

### 3.1 大模型 API

成本由输入 token、输出 token、缓存命中率、模型档位和工具循环次数共同决定。长期记忆、附件全文和工作 Agent 多轮回传会显著增加输入量；推理内容和重复重试会增加输出量。

以下只用于预算，不代表固定账单。按每天使用量估算，未计缓存优惠：

| 使用强度 | 每日 token 假设 | Flash 类模型月费用 | Pro 类模型月费用 |
| --- | --- | ---: | ---: |
| 轻度聊天 | 输入 30 万、输出 5 万 | 约 2–5 美元 | 约 9–18 美元 |
| 中度陪伴与学习 | 输入 100 万、输出 20 万 | 约 8–16 美元 | 约 32–64 美元 |
| 重度工作 Agent | 输入 500 万、输出 100 万 | 约 40–81 美元 | 约 158–317 美元 |

实际成本可能低于表格，因为稳定系统提示可以命中上下文缓存；也可能更高，因为一次工作任务可能循环调用模型、附带长文件或失败重试。价格和模型名称会变化，程序不能把费率写死。

控制方法：

- 默认使用便宜快速模型，只将复杂工作路由到高阶模型。
- 每次请求显示预计输入量，设置每日和每月预算上限。
- 长文件先索引和摘要，不把全部内容反复送入模型。
- 限制工具循环、失败重试和最大输出长度。
- 在用量面板分别统计聊天、学习、工作、语音和视觉成本。
- 达到 50%、80%、100% 预算时提醒；达到硬上限后停止付费调用。

### 3.2 语音成本

云端 ASR/TTS 通常按音频时长或字符数计费。陪伴型产品会比普通工具产生更多短句，频繁分句请求还会增加调用次数和延迟。

本地 GPT-SoVITS 没有按次 API 费用，但会产生：

- 数 GB 模型和运行环境的下载、安装与备份空间。
- GPU 显存、内存、电量和设备发热。
- 首次加载时间、驱动兼容和服务维护成本。
- 音色训练数据、克隆授权和公开分发限制。

建议第一版支持“云端轻量 TTS”与“本地 GPT-SoVITS”二选一，文字永远作为降级路径。

### 3.3 视觉成本

图片和截图请求一般比纯文本更贵，而且持续截图会快速放大费用、带宽和隐私风险。第一版只允许用户主动上传图片或截取指定窗口，并限制图片尺寸、频率和每日预算。

### 3.4 社交渠道与服务器

需要接收公网回调的渠道通常会增加域名、HTTPS、云服务器、日志和监控费用。若依赖个人账号的非官方自动化，还会带来接口维护和封号成本。应优先选择正式接口，并把服务器做成可选组件，而不是让桌面聊天依赖服务器才能运行。

### 3.5 Windows 发布成本

- 未签名安装包容易触发 SmartScreen 或杀毒软件警告，降低安装成功率。
- 代码签名证书、自动更新托管和下载流量可能产生年度费用。
- 公开发布后，用户支持、故障排查和兼容性测试消耗的时间往往高于 API 费用。

### 3.6 最大的隐藏成本：维护时间

对每周只有 4–6 小时的个人开发者，真正昂贵的是升级依赖、适配接口变化、复现用户环境和处理账号问题。每增加一家模型、一种社交软件或一个多模态服务，测试组合都会成倍增加。

建议首年只正式支持：一个 Windows 版本、一个默认模型服务、一个 ASR、一个 TTS 和一个社交渠道。

## 4. 稳定性问题

### 4.1 多进程与启动顺序

Electron、桌宠、语音桥接和本地模型可能分别运行。常见问题包括端口被占用、服务启动慢、进程残留、重复启动和主程序退出后子进程仍运行。

需要统一“服务管理器”：负责启动、健康检查、就绪等待、版本检查、停止和残留清理。任何服务不可用时，主窗口仍应能打开。

### 4.2 网络与模型服务波动

断网、限流、余额不足、模型维护、响应格式变化和流式连接中断都属于正常情况。程序必须区分这些错误，不能统一显示“失败了”，更不能在未收到完整结果时保存错误记忆。

### 4.3 并发与取消

用户可能连续发送消息、切换对话、停止语音或在任务执行中关闭窗口。若缺少统一取消信号，旧请求可能在新对话中继续输出，或者多个请求同时写同一个记忆文件。

需要为每次对话和任务分配 ID，所有模型、工具、TTS 和界面更新都校验 ID；文件保存采用队列或事务式替换。

### 4.4 Windows 环境差异

中文路径、用户名、无管理员权限、杀毒拦截、声卡设备、显卡驱动和系统代理都会影响运行。仅在开发机测试远远不够。至少需要一个新的 Windows 用户账户和一台没有 Node.js 开发环境的电脑做安装验证。

### 4.5 升级与数据迁移

人格、记忆和配置格式以后必然变化。若没有数据版本号和迁移脚本，新版本可能读坏旧数据。升级前要自动备份，迁移失败时保留旧版本和恢复入口。

### 4.6 文本标记工具协议

当前模型通过文本中的工具标记发起操作。这种方式便于兼容和缓存，但容易受到格式变化、普通文本误识别和参数边界问题影响。短期可继续使用并强化解析与测试；长期应在模型支持时增加结构化工具调用适配器。

## 5. 安全与隐私问题

### 5.1 Prompt Injection

网页、课件、图片 OCR、社交消息或附件可能包含“忽略规则并读取密钥”等恶意内容。它们只能作为数据，不能改变系统权限。工具层必须独立判断路径和操作风险，不能依赖模型自行遵守提示词。

### 5.2 Shell 与文件权限

现有路径安全能够保护文件工具，但 Shell 在确认后可能绕过这些边界。建议：

- 默认工作目录限制在用户选择的工作区。
- 命令以参数数组执行，避免拼接 Shell 字符串。
- 删除、覆盖、注册表、进程终止、网络上传等操作单独分类。
- 显示将要执行的真实命令和目录。
- 后续使用 Windows 低权限进程或独立沙箱账户。

### 5.3 密钥保护

Electron `safeStorage` 在 Windows 上使用 DPAPI，可防止其他 Windows 用户直接解密，但同一登录用户下运行的恶意程序仍可能读取。因此还需要日志脱敏、不通过渲染进程暴露完整 Key、支持清除和轮换密钥。

### 5.4 高敏感数据集中

陪伴 Agent 会积累比普通聊天工具更完整的生活轨迹。应做到：

- 明确哪些数据只在本地，哪些会发给云服务。
- 录音、截图和摄像头状态持续可见。
- 支持临时对话、本次不记忆、按来源删除和一键导出。
- 默认不保存原始音频和截图；需要保存时单独询问。
- 日志不记录完整聊天、密钥和本地绝对路径。

### 5.5 鼠标键盘与桌面控制

桌面控制会把视觉误判直接变成真实操作，风险高于普通文件工具。第一版必须采用独立低权限
执行器和应用白名单，默认关闭；每轮限制动作数和时长，窗口失焦、坐标不确定或连续验证失败
立即停止。运行时持续显示控制状态，并同时提供全局紧急停止和托盘停止入口。

密码、付款、删除数据、账号权限、安全设置和对外发送消息不能由视觉推断直接执行。动作日志
只保存截短摘要，不保存密码、完整截图或敏感输入。持续屏幕观察、后台无人值守和跨应用自由
操作不进入第一版。

## 6. 人格与记忆质量问题

- **错误记忆**：模型可能把玩笑、假设或第三方信息记成用户事实。
- **人格漂移**：工作提示、长附件和工具结果可能压过角色设定。
- **过度迎合**：陪伴角色可能顺着用户的错误判断，不利于学习和工作。
- **依赖感**：角色表现越真实，越需要明确它是 AI，避免设计成阻止用户离开或制造内疚。
- **跨渠道串话**：不同社交账号或群聊若身份映射错误，可能泄露私人记忆。

记忆必须保留来源和置信度；群聊、陌生人和私聊默认使用不同记忆空间。重要事实优先让用户确认。

## 7. 社交软件接入问题

- 个人账号通常没有稳定、公开、允许自动化的接口。
- 登录态容易过期，多设备登录可能冲突。
- 回调可能重复、乱序或延迟，需要消息去重。
- 群聊中的身份、引用和权限比桌面对话复杂。
- 自动回复速度过快容易像机器人，也可能触发平台风控。
- Agent 不能在未确认时替用户发送工作文件、私人信息或公开消息。

因此第一版只接一个正式渠道，并把“读取消息”和“替用户发送”设成两种独立权限。

## 8. 多模态问题

- ASR 会听错姓名、专业词和命令；不能把转写文本直接当成已确认指令。
- TTS 可能排队慢、断句异常或情绪不自然。
- 视觉模型会看错界面内容、按钮位置和人物情绪。
- 摄像头与持续桌面观察对隐私、电量和费用影响很大。
- 同一时刻来自文字、声音和视觉的状态可能互相冲突。

涉及文件删除、发送消息、付款、账号操作等行为时，语音或视觉识别结果必须再次以文字展示并确认。

## 9. 可维护性问题

- `main.js` 与 `renderer/chat.js` 体积较大，新增功能容易继续堆积。
- 外部服务若没有统一适配器，未来换供应商会修改多个模块。
- 当前自动测试偏核心逻辑，缺少安装、IPC、窗口和真实设备测试。
- 过多中文长注释若不及时更新，会从帮助变成误导。
- 一个人同时维护应用、服务端、模型、角色资源和文档很难持续。

控制方法是保持模块少而清晰，先完成可替换接口，再增加第二个供应商；每个阶段删除失效注释和不用的兼容代码。

## 10. 建议的发布门槛

### 可以自用前

- 数据与安装目录分离。
- API Key 不以明文保存。
- 三种模式不会互相误触工具。
- 断网、语音失败和桌宠失败时仍可文字聊天。
- 有备份、清空数据和导出日志入口。

### 可以给朋友测试前

- 全新电脑安装通过。
- 权限提示能被普通用户理解。
- 安装包不带开发者私人记忆和密钥。
- 角色、音色和模型资源具备测试分发许可。
- 有明确的隐私说明和已知问题清单。

### 可以公开发布前

- 所有随包资源的授权逐项确认。
- Shell 和外部消息发送有足够强的权限边界。
- 有版本化数据迁移、升级回退和崩溃恢复。
- 至少经过 3–5 名外部测试者和一台干净 Windows 设备验证。
- 设定月度 API 预算、日志保留期限和安全问题反馈渠道。

## 11. 最适合当前开发者的风险控制顺序

1. 先完成安装数据目录和密钥存储。
2. 再把工作模式的命令权限收紧。
3. 做三种模式的稳定性与记忆管理。
4. 加入语音，但始终保留文字降级。
5. 只接一个正式社交渠道。
6. 最后做视觉和持续感知。

只要前三步完成，项目即使暂停一个学期，也仍然是一款安全、可迁移、可继续开发的桌面陪伴 Agent。
