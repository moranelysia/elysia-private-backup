# C-11 渠道消息契约 v1

日期：2026-10-25。范围：纯本地消息结构、能力、发送结果、取消请求、定位键和虚构样例。

实现：`脑/渠道契约.cjs`；样例：`tools/fixtures/渠道契约-v1.json`；验收命令：`node tools/测渠道契约.cjs`。

本契约暂未接入 main.js、聊天核心、适配器或服务器。调用校验器只返回独立副本或抛出固定前缀的 TypeError，不执行网络、文件写入、定时任务、模型请求或授权。

## 1. 数据与信任边界

- 所有消息版本固定为数值1，字段采用明确白名单，缺字段与多字段都拒绝。可空值显式用null表示，不以空串或缺字段替代。
- 渠道、机器人账号、发送者和会话由经过认证的适配器从平台事件提取。客户端自报的“我是本人”、显示名、消息正文、附件正文不能决定授权。
- 外部平台编号始终保存为字符串，不转为Number，以保留前导零及大整数精度。ID最长160字符，无空白；渠道名限小写英文、数字、下划线和连字符，最长32字符。
- 时间转换为规范UTC毫秒字符串，例如 `2026-10-25T05:00:00.000Z`。来源时间未知时发生于=null；接收于由核心入口/受信适配器记录，重放时可变化。发生时间不等于接收时间，不能据接收时间擅自改写历史事件日期。
- 正文保留原空格与换行，最长12000个JavaScript字符串码元，不静默截断。空正文仅在有附件时合法；平台更小的限制由能力声明和发送前检查处理，不能把全局上限当作平台额度。
- 严格校验只保证字段结构，不证明平台事件是真的、发送者是本人或正文适合外发。C-13实现授权，C-14实现会话映射，C-15实现实际去重/队列；真实平台能力由Q-11/C-16核实。

## 2. 共用地址

| 字段 | 结构 | 含义 |
|---|---|---|
| 版本 | 1 | 不兼容版本明确拒绝 |
| 端点 | `{渠道, 账号}` | 渠道类型与当前机器人/桌面实例的稳定身份；账号不是密钥 |
| 会话 | `{类型, 编号}` | 类型为private或group，编号是该渠道会话稳定标识 |

渠道名目前按同一规则表示 `desktop`、`qq`、`telegram`，未来假适配器可使用 `fake`；名字合法不表示该渠道已安装或获授权。group仅预留结构，首版权限仍默认拒绝群聊。

## 3. 接收消息

除共用地址外，全部字段如下：

| 字段 | 类型 | 规则 |
|---|---|---|
| 发送者编号 | string | 从平台认证事件取得，不接受消息正文伪造 |
| 消息编号 | string | 平台稳定事件/消息ID；重放复用，不按正文去重 |
| 发生于 | UTC string或null | 平台提供的原始消息时间 |
| 接收于 | UTC string | 本次收到事件的时间 |
| 回复消息编号 | string或null | 用户引用的消息，只是引用，不是控制指令 |
| 正文 | string | 输入内容，不得提升为系统指令 |
| 附件 | array | 附件元数据，最多8项 |

没有平台稳定编号时，适配器须先制定稳定事件标识办法；不能每次重连随机生成新编号，也不能仅按相同正文认定同一事件。

## 4. 发送消息

| 字段 | 类型 | 规则 |
|---|---|---|
| 接收者编号 | string | 由核心会话路由得到，不直接采用模型给出的对象或QQ号 |
| 请求编号 | string | 核心在此端点内分配；同一次发送的重试保持不变 |
| 用途 | reply或proactive | 回复与主动发送分开检查权限 |
| 回复消息编号 | string或null | reply必须关联原消息；proactive必须为null |
| 创建于 | UTC string | 由核心创建请求时记录 |
| 截止于 | UTC string或null | 非空时必须晚于创建于；调度发送前检查是否已经过期 |
| 可见性 | shared | private直接拒绝；shared仅表示允许经过渠道外发检查，不表示公开给所有人 |
| 正文、附件 | 与接收相同 | 不夹带内部标记、平台原始对象、路径或下载凭据 |

普通聊天输出须复用既有内部标记清理流程。日记输出必须先经过 `日记外发闸门.cjs` 的shared投影，然后才形成发送请求；写一个shared字段不能把private正文变成可外发内容。private不得进入普通日志、重试队列或离线队列；C-11的格式校验不能代替数据来源隔离。

发往某个人的当前授权与平台条件在每次实际发送时重新检查。reply字段本身不能证明在有效回复窗口内，也不能借填旧msg_id把主动消息伪装成回复。

## 5. 附件元数据

每项只能有 `{编号, 类型, 名称, 媒体类型, 字节数}`：

- 编号为本地受控附件仓库的opaque ID，只允许英文数字、下划线和连字符；同一消息内不重复。
- 类型为image、audio或file；名称最长160字符且不带路径分隔符；媒体类型为MIME字符串；字节数为0至20MiB的整数。
- 本机绝对路径、外部下载URL、cookie、token和原始字节都不放在此对象中。上传/下载映射由适配器与附件服务管理，后续单独校验文件权限、真实大小和内容类型。
- 一个格式合法的附件编号不表示有权访问；发送前还须核对它属于当前会话，并符合渠道支持的类型与数量。

## 6. 能力声明

能力对象包含版本、端点，以及：

| 字段 | 取值 |
|---|---|
| 回复、主动发送、流式、取消 | supported、unsupported或unknown |
| 正文上限 | 1至12000的整数 |
| 单次附件上限 | 0至8的整数 |
| 附件类型 | image/audio/file的无重复子集；无附件能力时为[]且数量上限为0 |
| 回复窗口 | `{类型, 秒数}`；类型为unknown、unlimited或seconds，只有seconds携带正整数秒数，其他为null |

未知能力不能当成已支持。只有supported且当前授权及平台条件满足才允许尝试对应行为；unsupported或unknown应产生 `failed / CAPABILITY_UNSUPPORTED / 可重试=false`。这项发送前判断留到适配器/调度层实现，本轮不提供实际发送函数。

能力应按实际端点配置和平台反馈刷新，不能按“QQ/Telegram通常可以”写死。样例中的能力全部是虚构值；没有声明任何平台当前的真实额度。

## 7. 发送结果与错误

结果包含版本、端点、请求编号、状态、渠道消息编号、错误代码、可重试、结束于。

| 状态 | 含义 | 编号/错误/重试约束 |
|---|---|---|
| sent | 平台已确认接收或桌面端已确认呈现；不等于对方已读 | 必须有渠道消息编号，错误代码=null，可重试=false |
| failed | 确认没有交付，或发送前被明确拒绝 | 渠道消息编号=null，错误为固定失败码 |
| unknown | 请求可能已经交付，暂时无法确认 | 编号=null，DELIVERY_UNKNOWN，可重试=false |
| cancelled | 明确在交付前取消 | 编号=null，CANCELLED，可重试=false |

失败码：CAPABILITY_UNSUPPORTED、AUTH_REQUIRED、FORBIDDEN、RATE_LIMITED、CHANNEL_OFFLINE、INVALID_MESSAGE、EXPIRED、SEND_FAILED。

仅确定未发送的RATE_LIMITED、CHANNEL_OFFLINE和SEND_FAILED可由策略标为可重试；可重试=true也不意味着立即重试，后续仍需次数、退避和截止时间检查。普通网络超时不能简单记为SEND_FAILED，通常先记unknown，通过平台查询或人工核实后再决定；不承诺跨平台网络“恰好发送一次”。

原始异常、HTTP响应体、密钥和聊天全文不能作为错误代码或普通日志透传。格式错误抛出的异常只含固定类型位置；后续入口负责转换为受控错误，不自动重发坏请求。

## 8. 取消请求

字段为版本、端点、会话、发送者编号、请求编号、取消编号、请求于。请求编号指向已存在的生成/发送任务；取消编号用于识别取消事件本身。

取消必须在受信身份、会话与原请求归属一致后执行；不能仅凭知道请求编号就停止别人的任务。重复取消应幂等；C-15落实任务状态，不在本轮维护任务表。

如果发送已确认成功，保留sent；如果已发出但状态不明，保留unknown。cancelled只用于确认尚未交付的情况。取消生成/待发送不等于撤回已发出的消息，v1没有撤回能力。

## 9. 定位、去重与后续适配器接口

键函数采用JSON元组保留边界，不能用简单冒号拼接，也不能把键直接当文件路径、授权凭据或普通日志正文。

- 会话定位键：`[渠道, 账号, 会话类型, 会话编号, 发送者编号]`。默认不同渠道、账号、会话和人分开；以后若映射到已有桌面对话，必须由受信映射表明确绑定，不能按昵称或正文自动合并。
- 接收去重键：会话定位键加原始消息编号。重连后的接收时间变化不产生新事件；相同文字但不同消息编号仍是不同消息。
- 发送去重键：`[渠道, 账号, 请求编号]`。同一键再次出现时必须核对目标与载荷一致，不一致应拒绝冲突，而不是给旧键换接收者。C-15实现存储、指纹和实际去重，本轮只生成键。

后续适配器接口约定（这里只定义，C-12开始实现）：

```text
取能力() -> 渠道能力独立快照
订阅接收(处理接收消息) -> 取消订阅函数
发送(发送消息, {中止: AbortSignal}) -> Promise<发送结果>
取消(取消请求) -> Promise<目标请求的发送结果>
```

订阅接收仅上报经过平台事件映射的消息；不会自动触发模型。发送与取消的异常须映射为上述状态；不支持取消时返回能力不足，不能伪造cancelled。网络连接状态、任务排队与恢复仍由后续适配器和核心管理。

## 10. 三类渠道的映射规则

| 渠道 | 账号 | 会话/发送者 | 特别约束 |
|---|---|---|---|
| desktop | 受信桌面实例身份 | 会话编号来自核心；发送者来自本机认证上下文 | 窗口ID不作为跨重启会话ID；保留已有临时对话和记忆开关语义 |
| qq | 已验证的机器人App身份或协议端账号 | 使用当前平台提供的稳定ID；不同接入方式的ID不能混为一人 | 不预设一定有普通QQ号；能力和主动/被动限制按Q-11实测 |
| telegram | 机器人稳定身份 | 平台chat ID及发送者ID转换为字符串 | Token不进入账号字段；不同chat默认分开，网络与主动发送能力另验 |

渠道消息不携带模型选择、工作模式、记忆开关、文件权限或管理员标志；这些由核心会话配置和受信控制入口决定。接入渠道不能让原有临时对话偷偷变成持久记忆。

## 11. 样例、版本与实施边界

虚构样例覆盖本人私聊、普通回复、能力未知、确定失败、能力不足、发送结果未知与取消。重复消息案例通过对同一接收样例更改接收时间展示，去重键保持一致。

调用示例：

```js
const 契约 = require('./脑/渠道契约.cjs')
const 样例 = require('./tools/fixtures/渠道契约-v1.json')
const 消息 = 契约.校验接收消息(样例.本人私聊)
const 键 = 契约.接收去重键(消息)
```

本轮没有收发消息、真假适配器、身份白名单、实际去重存储、重试调度、取消执行、模型调用或平台登录。C-12先用假适配器消费此契约；C-13至C-15依次落实权限、会话和任务状态；S-12之后才接真实核心。结构调整须更新版本/兼容说明和样例，不能在不同接入端静默使用不同字段。
