# S-16D3 C3E2：轮次恢复容量与保留策略评估

## 已核实的限制

- Worker 运行回执最多 2048 条、整个回执日志最多 1 MiB，先达到任一限制都会拒绝写事务；不会自动淘汰或伪造成功。一次成功的绑定对话至少需要预留+started、可能发送、结果+succeeded、聊天提交四条回执；不考虑其他事务及字节上限，理论上限最多约 512 轮，实际可能更少。
- 虚构模型轮次最多 10000 条、绑定最多 2048 条，均不会自动删除；用量事件最多 10000 条。暂存正文最多 8000 个 JS UTF-16 代码单元且不超过 32000 字节，成功聊天提交后清除；未决结果留存，如何最终清理还没有定义。
- Worker 单条输入最多 65536 字节，输出最多 262144 字节；核心读取两页、每页至多 200 条历史，历史和提示各有 131072 字节校验，但 Worker 输入上限可能更早生效。所有这些是隔离实现的硬边界，不是已验证的生产容量。
- 四个数据库阶段的进程终止与旧快照隔离已按 `验收-绑定核心跨进程恢复-S16D3C3D3-2026-10-28.md` 测试；取消和 Worker 故障由前述专项覆盖。并不等于真实断电、磁盘损坏或供应商恰好一次。

## 需要选择的后续方向

**A：设计可核验的分段归档（推荐）。**将历史请求关联、必要的防重墓碑、用量与操作回执按有序分段保存，归档切换和恢复必须有可验证的关联与保守隔离；清理正文与保留墓碑分开设计。优点是为长期运行提供可持续路径，备份与恢复边界更明确；缺点是需要新增数据格式、迁移/校验、容量和故障测试，工作量较大；归档仍会增长，不意味着无限空间。

**B：只扩大现有隔离回执上限，随后再设计归档。**优点是改动小、能延长模拟测试；缺点是整体 JSON 仍随使用增长，写入成本和内存上限需要实测，根本问题仍在，不能当作生产可持续方案。

**C：保持现状，容量满时停止。**改动和现阶段风险最低，但长时间使用会不可避免地中断；后续仍需规划归档和恢复。

以上为架构建议而非已验证实现。真实数据的保留时长、删除、隐私与备份范围应在实施 A 前单独明确；不能为了腾空间删除不确定轮次或防重依据。由于涉及保留策略和显著实现范围，等待用户选择；不修改正式数据、不扩大限额、不上传或部署。
