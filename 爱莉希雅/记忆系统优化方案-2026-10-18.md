## 一、书里的核心框架（要照着改的东西）

### 1. 记忆的四层结构

| 层 | 人类对应 | Agent 对应 | 我们现在的实现 |
|---|---|---|---|
| **工作记忆** Working | 当前上下文 | 上下文窗口 + 当前任务状态 | 对话上下文（已有） |
| **情景记忆** Episodic | "上周三在哪吃了什么" | 带时间戳的事件序列 | 日记 J1/J2（**部分覆盖**） |
| **语义记忆** Semantic | "意大利首都是罗马" | 从多次交互提炼的稳定特征 | 长期记忆事实（**已有，但没分层**） |
| **程序记忆** Procedural | 骑车的能力 | 反复做同一件事形成的流程 | **完全没有** |

> 我们的长期记忆目前是**扁平的事实库**，把三类混在一起。书里的建议是分三类存储、检索时按类型路由。

### 2. 三层压缩策略（与用户手写笔记完全一致）

```
第一层  重要性评分筛选
        ├─ 访问频率（经常被召回的记忆更重要）
        ├─ 时间衰减（越久远越容易被遗忘）
        ├─ 情感强度（带强情绪标记的更易保留）→ 与情感层 E1 绑定
        └─ 信息独特性（重复信息重要性降低）
        低于阈值的标记为可压缩/可删除

第二层  聚类
        相似记忆分组 → 每组生成代表性摘要
        （例：多次天气对话 → "用户经常询问天气，特别关心降雨"）
        原始详细记忆存到二级存储

第三层  抽象与泛化
        从具体情景记忆提取一般规律 → 转成语义/程序记忆
        （例：多次购物对话 → "偏好性价比高的产品，重视用户评价"）
```

**用户的笔记**：一、重要性评分（访问频率：主动联想/被动找回；情感强度→与记忆情绪层绑定；信息独特性/硬记忆）、二、分类、三、自我学习，将记忆抽象与泛化。

**结论：书里的方案和用户的想法是一致的，直接照做。**

### 3. Mem0 vs Memobase 的取舍

| | Mem0 | Memobase |
|---|---|---|
| 定位 | 通用记忆流水线（事实条目） | **用户画像 + 事件记忆** |
| 画像 | 无 | `basic_info→姓名`、`interest→兴趣`、`work→职位` 两级组织，开发者控制粒度 |
| 事件 | 有 | 按时间线记录，回答"上次讨论预算是什么时候" |
| 成本 | — | **缓冲批处理**：对话累积到一定规模/时限才触发一次提取，摊薄 LLM 调用 |

**可借鉴的两个工程点**：
1. **缓冲批处理** —— 我们现在是每条消息后都跑提取，可以改成累积触发（省钱 + 降延迟）
2. **画像槽位** —— 给用户画像定义固定槽位（姓名/兴趣/职业/作息…），比自由事实更好用

### 4. JSON Cards / Advanced JSON Cards

- **JSON Cards**：三层嵌套 `类别→子类别→键值对`（如 `personal.contact.email`），支持**部分更新**（改 `work.position.title` 不动 `work.company.name`）
- **局限**：刚性结构假设信息可清晰分类，但"周末用 Python 开发个人项目"同时涉及时间偏好/技术偏好/活动类型，强制归一类会丢多维
- **Advanced JSON Cards**：每张卡加 `backstory`（为什么存这条）、`person`（为谁存）、`relationship`（和用户什么关系）、时间戳
  - 解决歧义："张医生"可能是用户的牙医，也可能是用户父亲的心内科医生
  - 解决多身份：为自己 / 为父母 / 为子女存的信息要能区分

**对我们的启示**：长期记忆条目应该加 `来源/为谁/为什么` 三个字段，而不是只有"事实 + 时间"。

### 5. 五类工具（第 4 章，顺带记录）

| 类型 | 调用方向 | 作用对象 |
|---|---|---|
| 感知工具 | Agent 主动 | 获取信息（web_search / knowledge_base_search / fetch_url） |
| 执行工具 | Agent 主动 | 改变世界 |
| 协作工具 | Agent 主动 | 驱动其他 Agent 或人类 |
| 用户沟通工具 | Agent 主动 | 向用户传递信息 |
| 事件触发工具 | Agent 注册、外部触发 | 驱动 Agent 开始执行 |

**我们的工具治理（T0-T3）目前只覆盖了"感知"和"执行"两类**，缺"事件触发"这一类 —— 主动陪伴 P1 其实就是事件触发工具，但没按工具的形式注册。

## 三、差距清单（按价值排序）

### P1｜记忆分层（第一步已完成基础分层）
- [x] 给记忆条目加 `记忆类型` 字段：`episodic` / `semantic` / `procedural`
- [x] 提取时自动判定类型（时间+事件→情景；特征→语义；流程→程序）
- [x] 检索时按类型路由（问"什么时候"→查情景；问"我喜欢什么"→查语义；问"怎么做"→查程序）
- **工作量**：中。数据层加字段 + 提取 prompt 改造 + 检索分流

### P2｜三层压缩（第二、三层是空白）
- [x] 第一层：重要性评分 + 时间衰减。召回时间分采用 7 天半衰期；高重要性记录有可解释的
  衰减下限。时间只改变仍有效候选的排序，不自动删除记忆，过期仍由原生命周期规则负责。
- [x] 第二层最小候选层：本地严格聚类 + 抽取式摘要候选；保留全部原文，只写独立缓存，
  不接入召回、不改原记忆。
- [x] 第二层自动就绪门控：启动、每 30 分钟和记忆变化后低频重算只读候选；无候选时明确保持
  “等待真实候选”，有候选时只开放“待人工审核”，生产闭环始终关闭。真实数据当前 41 条符合资格、
  0 组达到阈值。
- [ ] 第二层生产闭环：人工审核、二级存储与安全召回；必须在出现真实候选并验收分组质量后再定。
- [ ] 第三层：抽象泛化（情景 → 语义/程序）
- **工作量**：大。第二层要聚类（可用 embedding + 阈值），第三层要定期跑批

### P3｜记忆条目加元数据（Advanced JSON Cards 的做法）
- [x] `backstory`（为什么存）/ `person`（为谁）/ `relationship`（关系）
- [x] 支持"为父母/为子女"多身份区分（第三方人物必须能在用户原话中找到，关系使用受控值）
- **工作量**：小 —— 加字段 + 提取 prompt 里加三项输出

### P4｜缓冲批处理（Memobase 的省钱技巧）
- [x] 提取改成累积触发：同一正式对话累计 3 轮，或从首轮起等待 5 分钟后跑一次。不同对话
  独立缓冲，候选必须标注依据轮次并通过对应用户原话的逐字校验。
- **工作量**：小 —— 调度层改，不动提取逻辑

### P5｜程序记忆（全新）
- [ ] 从重复任务卡里提炼"常用流程"
- [ ] 下次遇到相似任务时提示"上次是这么做的"
- **工作量**：大，且需要足够多的实际任务数据才有意义 → **先不做**
