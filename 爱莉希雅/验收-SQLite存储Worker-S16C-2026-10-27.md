# S-16C 专用存储Worker、单写队列与恢复验收

日期：2026-10-27；源码基线 `10e6198`，实现提交见共同协作本步记录。本轮只做C；独立Node中一个存储Worker、一个连接，不接Electron、正式记忆、模型或真实渠道。

## 代码与协议范围

- [sqlite-worker.cjs](storage/sqlite-worker.cjs)：主线程监督、有界队列、超时/背压、显式恢复与关闭。新建盘库仍走B，C只打开已经校验的临时隔离盘库，不接受任意脚本、Worker路径、预载、SQL或新建路径。
- [sqlite-worker-thread.cjs](storage/sqlite-worker-thread.cjs)：专用Worker实际开盘、执行命令；[协议白名单](storage/sqlite-worker-protocol.cjs)限定操作和参数个数。**C只开放会话登记/更新/整轮三种写操作**，验证运行机制；另有受限会话/记忆统计、长期列表、shared日记、旧档分页等读取。完整记忆/日记/状态写入和核心注入在D逐项适配，不把通用反射调用当全仓储接线。
- [sqlite-worker-owner.cjs](storage/sqlite-worker-owner.cjs)：Windows命名管道排他持有；端点仅作为OS持有锁，连接即关闭，不传业务数据，也没有TCP/公网监听。Linux有抽象socket分支，**本轮未在Linux验收**。[Node IPC规则](https://nodejs.org/download/release/v26.8.2/docs/api/net.html#identifying-paths-for-ipc-connections)

主线程做排队及有界目录身份检查，SQL/事务/全库核验在Worker。同步SQL等待时，主线程定时器和本地监督状态仍响应；这不是整机性能或所有文件I/O均异步的承诺。状态不含正文、根路径或所有权令牌，`ready`是监督状态，不是每次重新全库检查的健康证明。

## 限额与失败语义

| 项目 | 当前默认/边界 |
|---|---|
| 总待办数 | 32，包含一个在途请求；可配置1至256 |
| 等待请求JSON字节 | 默认1MiB，硬配置范围1KiB至8MiB；不把它称作进程内存上限 |
| 单条输入/结果 | 输入64KiB、结果256KiB；纯数据、UTF-8、字段/操作/参数数量校验，getter/函数/原型对象拒绝 |
| 命令期限 | 默认5000ms，从入队计算；超限已排队请求明确未执行，在途结果按unknown/interrupted处理并封闭执行器 |
| 启动/退出确认 | 默认10000ms，有界等待；退出没确认时保留排他持有，不能假装停止后让第二写者接管 |
| Worker JS堆 | old 128MiB/young 16MiB；不包含全部native/Buffer/RSS，不保证隔绝进程整体OOM |
| 命令回执日志 | 最多2048条、1MiB；满则拒绝新写，不自动淘汰旧条目削弱幂等 |

生产入口固定Worker文件、`execArgv=[]`、独立环境白名单，只传必要OS临时路径和时区，不继承任意ELYSIA凭据变量。测试预载故障仅通过测试脚本中的Worker构造器替身注入，生产选项/命令不接受故障参数。[Worker限制和生命周期](https://nodejs.org/download/release/v26.8.2/docs/api/worker_threads.html)

写操作必须带稳定 `操作编号`；请求指纹与原成功结果随业务同一SQL事务保存。相同ID/参数回原结果，异参数拒绝；回执写失败整个事务回滚，不返回伪成功。Worker提交后但回复前中断，调用方只能先查回执再决定，不自动重做模型或发送。未发送给Worker的排队请求明确 `not-started`；在途写可能已提交，明确 `unknown`。

故障后 `.恢复()` 必须等待原Worker真实退出，再核对身份并启动新Worker，不重放原队列。无法确认退出或失去OS持有则有界报错并保持拒写。`.关闭()` 拒新请求、处理已接收队列并等待退出；故障/超时不能报干净停止，恢复和关闭并发也不能提前放锁。[Node终止/退出接口](https://nodejs.org/download/release/v26.8.2/docs/api/worker_threads.html#workerterminate)

## 所有权与磁盘格式

基础B旧锁版本1不自动接管。C声明包含版本2、随机会话令牌、进程ID、启动会话标识，以及根/目录/数据库文件身份。

恢复前先取得OS排他持有并复核目录/数据库身份，再核对锁内容与文件身份未变化；仅两种情况允许回收：本监督器的原Worker退出已确认且声明完全匹配；或旧C持有者进程经系统查询明确不存在。PID还活着、权限不明、未知格式、身份不符都拒绝，**不单凭PID/超时删锁**。测试用当前活PID验证拒绝，没有制造真实系统PID复用；原进程真实异常退出的路径另行实际验证。[Node进程查询](https://nodejs.org/download/release/v26.8.2/docs/api/process.html#processkillpid-signal)

这是受控协作进程的排他/恢复机制，不是对设备所有者的访问隔离。文件校验和用来发现损坏，不是对本机恶意篡改的密码认证。

物理`application_id/user_version=2`和原20表不变；盘保全子格式由1升至2，新增版本化 `disk_worker_receipts` 与其自身完整性指纹，和业务原文元数据同事务提交。缺日志/坏日志拒绝启动，不补空。子格式2盘库拒绝B旧直连入口，防止绕过Worker产生不受记录的写入。

**E的必要门槛：** B旧v2至v5逻辑候选包仍排除盘私有键，因此它们不是完整的Worker运行恢复包。C保证同一磁盘世代重启后的回执；E必须把运行回执和世代信息与数据库/外部文件一并保全，验证物理及扩展逻辑恢复都不丢幂等状态，不能直接把B逻辑包当可续跑的C备份。本轮没有提供Worker备份/导入命令，未声称此项已完成。

以上是 C-09O 对既定所有权/回执/背压要求的实现细化；E的备份内容随新增运行状态补全，不改变C→D→E→F→G顺序。
