## 1. 结论一：交付物可以不是 PSD（影响最大）

`PSD_LAYER_SPEC.md` 第 13 行：

> 由程序拆好的部件（例如 AI 分层的结果）可以不经 PSD，写成 Layout 清单交给 PSD2Live：
> 一个 JSON（或根目录放着它的 zip），逐层写明图片、画布矩形、上下顺序、组、标签、差分，
> 以及是否只作参考（如拆件前的原图，显示在画布上但不生成、不导出）。

最小结构：

```json
{
  "format": "psd2live-layout",
  "version": 1,
  "name": "Elysia-Hair-Sample",
  "canvas": { "width": 1145, "height": 1374 },
  "groups": [{ "path": "hair-back", "visible": true, "opacity": 1 }],
  "layers": [
    {
      "name": "80-02_back_hair_l_outer",
      "image": { "path": "parts/80-02_back_hair_l_outer.png", "width": 1048, "height": 1016 },
      "rect": { "left": 795.67, "top": 562.67, "width": 349.33, "height": 338.67 },
      "group": "hair-back",
      "tags": ["hair", "back", "left"]
    }
  ]
}
```

### 必须遵守的硬约束（原文逐条摘）

| 约束 | 数值 / 规则 | 出处 |
|---|---|---|
| `format` | 固定 `psd2live-layout` | 顶层字段表 |
| `version` | 整数，当前 `1`；比程序新则拒读 | 同上 |
| `canvas` | 单边 1–8192，**合计 ≤ 16 MP** | 同上 |
| 图层数 | 1–4096 | 同上 |
| 单张图片 | ≤ 16 MP、≤ 1 GiB | 文件与压缩包 |
| 图片路径 | 相对清单、用 `/`、不含 `..`、`.` 段、反斜杠、盘符，不得跳出清单所在文件夹 | 图层表 |
| `image.width/height` | **必须与实际图片一致**，否则整份拒绝导入 | 同上 |
| 清单体积 | UTF-8 JSON，≤ 16 MiB | 文件与压缩包 |
| 图层顺序 | `layers` **从后往前**：后列出的画在上面 | 上下顺序 |
| 侧别 | 同一图层不能同时有 `left` 与 `right` | 标签 |

**读取是原子的**：任何一处错误都会停止并说明位置（如
`layers[3]: parts/face.png is 808x935 pixels, the manifest says 800x935`），不会部分导入。

**对 `01-拆层设计表.md` 第 290 行的影响**

> 原：| PSD 合成与导入检查 | 4～8 小时 | 可交给 PSD2Live 的素材包 |

这一步有条件改成"**生成布局清单**"：由脚本产出 JSON + PNG，人工只做清单核对。
但**不能整步删掉** —— 清单对的地方只是格式，层序、左右、遮挡关系仍然要人看一眼，
规范自己也写了："命名成功不代表自动造型已通过验收。"

## 2. 结论二：逐层尺寸 —— 我们现在存图是浪费的

这是最容易白扔工时的一条。规范里 `image.width/height`（图片像素）和
`rect.width/height`（在画布上占多大）**是两回事**：

> 与 PSD 不同，图片的像素数不必等于它在画布上的大小：小部件可以带比画布更多的像素，
> PSD2Live 按逐层尺寸保留它们，纹理因此更密。

> 像素尺寸与矩形之比就是纹理密度：`126 × 147` 的图片铺在 `101.65 × 118.63` 的矩形上，
> 每画布单位约 1.24 个纹理像素。

而我们现在的每一层都是**整张 3435×4122 全画布 RGBA**。实测裁到 alpha 边界的结果：

| 层 | 现在（全画布） | 裁到 bbox 后 | 省 |
|---|---:|---:|---:|
| `80-01_back_hair_top` | 3.45 MB | 1.79 MB（2091×1926） | 49.4% |
| `80-02_back_hair_l_outer` | 0.29 MB | 0.21 MB（1048×1016） | 27.5% |

**一个必须提前知道的坑**：单图上限 16 MP、单边 8192。现在的 3 倍母稿
3435×4122 = **14.16 MP**，已经贴着 16 MP 了。
**一旦提高精度到 4 倍（4580×5496 = 25.2 MP），全画布存法会被直接拒绝导入。**
裁到 bbox 之后，单层只剩 1–4 MP，这条路才留得住升级空间。

## 3. 结论三：侧别写进 `tags`，不要靠文件名

`PSD_LAYER_SPEC.md`「左右与拆分」确认了一条与我们目测一致的约定：

> 左右指角色自身：**角色左侧通常在画面右边**。

（即 80-02 / 80-03 这种"角色左侧、画面右侧"是对的。）

但同一节给出的侧别写法是 `eyelash-l`、`eyelash-r`、`eyelash_left`、`左睫毛` 这类，
**没有 `xxx_l_mid` 这种孤立单字母的例子**。我们现在的文件名 `80-03_back_hair_l_mid.png`
里的那个 `_l_` 是否能被识别成左侧，规范里找不到依据。

干净的解法是清单第 98–99 行：

> `tags` 中的部位词与 `left` / `right` 决定部件与侧别……**含部位词时，部件与侧别都取自 `tags`**。
> 不含部位词或省略 `tags` 时，才按图层名识别。

所以：**`tags: ["hair", "back", "left"]` 比任何文件名都可靠**，也不受"数字前缀"干扰。
文件名继续按拆层设计表编号走，识别交给 tags。

## 4. 顺带值得知道的四件

1. **`reference: true` 是现成的对照层**：只显示、不进 Rig、不参与生成，也不需要标签。
   把原图以参考层放进清单，就能在 PSD2Live 里直接做中立态比对 —— 这正是我们
   `32-SAM2.1-Tiny试切报告.md` 里提到"从原图重新合成中立态的视觉比对"那一步。
2. **PSD2Live 自带本地 MCP 服务，180 余项公开操作**，与界面共用编辑命令与历史，
   支持原子批量与试运行。README 明确点名 Claude Code、Codex 这类 Agent 可直接读写工程。
   意味着拆完之后"绑定"这一段可以由 Agent 驱动，不必全靠鼠标。
3. **平台与运行**：Windows 10/11 x64 有便携版 ZIP / EXE，**自带 Java 运行时**；
   本机目前既没装 PSD2Live，也没有 `java`。
4. **许可**：GPL-3.0 / MIT 双许可，商用与本机自用都不构成障碍。

## 5. 本轮实测（样本：已完成的 80-01 + 80-02）

产物在 `拆分工作/布局清单试验/`，详述见 `拆分工作/37-布局清单试验说明.md`。

- 画布 1145×1374（1 画布单位 = 1 倍设计稿像素），图片保留 3 倍像素 ⇒ **纹理密度 3**。
- 按规范逐条校验 **33 / 33** 通过（格式、版本、画布上限、路径合法性、尺寸一致、
  标签冲突、组路径唯一等）。
- **像素级验证**：把清单描述的摆放合成回 3435×4122，与直接合成原始两层
  **逐像素完全一致**（`ImageChops.difference` 的 bbox 为空，1x 渲染最大通道差 = 0）。
- 即：清单承载的位置、尺寸、层序没有信息损失。

## 7. 下一步建议

1. **拍板画布单位**：模型画布定 1145×1374（当前样例）还是 3435×4122？
   这决定以后所有层的 `rect` 与纹理密度，越早定越省返工。
2. **把"裁到 bbox + rect 还原"写进正式流程**：80-03 之后的每一层都按这个存法产出，
   否则 4 倍精度那一步会撞 16 MP 上限。
3. **每层带 `tags`**：`["hair","back"]`、`["hair","back","left"]`、`["hair","back","right"]`，
   不靠文件名判断侧别。
4. 拿到 PSD2Live 便携版后，先导入这份样例清单核对，再继续拆 80-03。
