## 1. 时间假设与完成标准

本方案按以下现实条件安排：

- 每周投入约 20 小时，建议分成四个 3–4 小时开发块和一个 4–6 小时集成测试块。
- 两周形成一个可以安装、演示或实际使用的小版本。
- 考试周允许完全暂停，不安排必须按日期完成的外部承诺。
- 同一时间只推进一个主功能；发现新想法先放入待办，不立刻插入开发。
- 短期只供本人使用，公开分发、代码签名、角色资源再授权和陌生用户支持暂缓。
- GPT/Codex 与 DeepSeek Harness 穿插使用，具体分工见 `Agent协作约定.md`。

预计进度：

| --- | ---: | ---: |
| 可安装基础版 | 10–15 小时 | 约 1 周 |
| 三种模式稳定可自用 | 45–65 小时 | 累计 3–4 周 |
| 记忆可控、工作稳定 | 90–120 小时 | 累计 5–7 周 |
| 工具结果可信、可检查 | 120–165 小时 | 额外约 2–3 周 |

## 2. 产品范围

### 近期主线（前 8–10 周）

1. Windows 安装包与首次启动引导。
2. 聊天、工作、学习三种模式稳定运行。
3. 可查看、修改、删除和导出记忆。
4. 基础语音输入与语音回复。
5. 崩溃后恢复、日志导出和数据备份。

### 主线完成后再做

1. 一个使用官方接口或明确允许自动化的社交渠道。
2. 图片、指定窗口截图等主动视觉输入。
3. 对指定窗口的受控鼠标键盘操作。
4. Live2D 或其他角色外壳的标准适配接口。
5. 插件系统、自动更新和公开测试发布。

### 暂时不做

- 同时支持多家社交软件。
- 持续监控屏幕、摄像头或麦克风。
- 自研大模型、语音模型或完整 Agent 框架。
- 多 Agent 自动协作、复杂可视化工作流和插件市场。
- 为了演示而重写当前已经通过测试的核心逻辑。

## 3. 技术架构

```text
桌面窗口 / 系统托盘 / 社交渠道
                │
                ▼
        输入标准化与用户身份映射
                │
                ▼
         模式与上下文编排器
       ┌────────┼────────┐
       ▼        ▼        ▼
     聊天      工作      学习
       │        │        │
       └────────┼────────┘
                ▼
     模型适配器 / 记忆 / 工具权限
       ┌────────┼────────┐
       ▼        ▼        ▼
      TTS      ASR      视觉理解
                │
                ▼
     文字 / 声音 / 角色动作 / 文件产物
```

实现时坚持五个边界：

1. **安装目录只读**：程序代码放安装目录，聊天、记忆、配置、日志放 Electron `userData` 目录。
2. **外部服务适配器化**：模型、ASR、TTS、视觉和社交渠道都只实现统一接口，避免核心代码绑定供应商。
3. **模式共享身份、隔离工作数据**：三种模式共享用户身份和必要长期记忆；工程日志、教材全文等大数据不进入陪伴上下文。
4. **采集必须可见**：录音、截图和摄像头使用时显示明确状态，默认关闭。
5. **角色资源可替换**：人格卡、音色、Live2D 模型与程序分开打包，公开发布前分别确认授权。

## 4. 分阶段制作计划

### 阶段 A：可安装基础版（第 1 周）

任务：

- 接入 `electron-builder`，生成 Windows NSIS 安装包和免安装压缩包。
- 把运行数据从项目目录迁移到 `%APPDATA%` 或 `%LOCALAPPDATA%` 下的独立目录。
- 首次启动时复制全新人格模板并创建空记忆。
- 制作首次启动向导：选择模型、填写 API Key、测试连接、选择数据目录。
- 用 Electron `safeStorage` 加密本机凭据，界面不回显完整 Key。
- ~~增加“打开数据目录”和“备份数据”入口。~~ **0.2.2 已完成**：后台导出 ZIP，排除 Key 与缓存。
- 增加“导出日志”和“恢复数据”入口；恢复前必须自动备份现有数据并支持失败回滚。
- 在一个全新 Windows 用户目录下完成安装、启动、卸载和重装检查。

验收标准：

- 只拿一个 `Setup.exe` 就能安装。
- 不需要 Node.js、命令行或手动复制角色卡。
- 首次对话不知道旧用户姓名和经历。

### 阶段 C+：工具能力治理（当前优先，预计 30–45 小时）

这不是单独修天气。当前文件、命令、联网搜索、浏览器和外部编码 Agent 的返回格式与成功判据

搜出披萨店只是第一个清楚暴露出来的样本。此阶段先把工具层变成可检查的证据链，再继续扩展能力。

1. **T0 工具盘点与基线（6–8 小时）**

   - 为搜索、读取、写入、列目录、Shell、浏览器和外部编码 Agent 各保留真实成功、无结果、
     错结果、超时、权限拒绝和中途取消样本。
   - 找出“操作执行成功但目标未完成”的入口，按影响排序；天气无关结果列为第一条固定回归样本。
   - **2026-10-15 已完成**：9 个已登记工具、嵌套调用与工具记录均已盘点，现有测试基线和
     13 个首批失败样本已整理到 `工具能力盘点-2026-10-15.md`。确认当前没有真正的浏览器控制或
     外部编码 Agent 工具；最大缺口是 `.好` 同时代表执行、结果和目标三层成功，且取消链路不完整。
2. **T1 统一工具回执与完成闸门（8–12 小时）**

   - 区分“执行成功、部分完成、结果不可靠、明确失败”；模型不能把后三种改写成已完成。
   - 工作任务卡的最终状态由本地回执和后置验证决定，不只依赖模型文字。

## 5. 每周工作方法

建议固定成五个工作块：

| 时间块 | 内容 |
| --- | --- |
| 第一次 3–4 小时 | 明确任务卡，处理架构或高风险部分 |
| 第二次 3–4 小时 | 实现本周唯一主任务 |

每次开始前只写一句可验证目标，例如“新电脑不装 Node 也能启动”，不要写“完善安装系统”。每次结束必须留下能运行的提交或安装包。若一个任务连续两周无法完成，就把它再拆成两个更小任务。

## 6. 测试与发布规则

每次发布只做四层验证：

1. 运行现有本地自动测试，目前基线为 523/523。
2. 做三种模式各一次手动对话。
3. 在空数据目录启动一次，确认没有旧人格和旧记忆。
4. 安装版执行安装、首次启动、退出、重启和卸载。

语音、视觉和社交渠道加入后，各自增加一条成功路径和一条断网/服务不可用路径。除非修改了对应模块，不重复运行昂贵的联网模型测试。

## 7. 学业优先时的暂停策略

- 期中、期末前两周只修严重错误，不开发新功能。
- 每个阶段结束都打一个版本标签并保存安装包，保证随时可暂停。
- 灵感统一写进 `待办.md`，不在复习期间动代码。
- 若某学期只能完成一个目标，优先顺序是：安装包 → 三模式稳定 → 记忆可控 → 工具可信 → 语音 → 社交 → 视觉 → 受控桌面操作。

最关键的阶段是前三个。完成 `0.4.0` 后，它已经是一个可以长期自用、能继续成长的桌面陪伴 Agent；后面的语音、渠道、视觉和桌面操作都是可独立增加的能力，不会推翻前面的成果。
