## 一、这份文件解决什么问题

这份文件是项目从现在开始的唯一“步骤顺序账本”。它不替代各模块的详细设计文档，而是负责：

1. 保存最初方案，防止后来新增要求覆盖原始意图；
2. 明确当前真正执行到哪一步；
3. 新增或修改要求时记录来源、影响和可行性；
4. 按依赖、安全性和用户目标重新排序，但绝不悄悄删除旧顺序；
5. 每完成一步，同时更新本文件和 `共同协作.md`；
6. 阶段快结束时主动提醒用户，先讨论新内容，再决定下一阶段。

如果本文件与旧日志的“下一步”冲突，以本文件最新的“当前执行顺序”为准；旧日志继续作为历史证据。

## 二、强制记录规则

### 1. 状态只能使用以下七种

- `已完成`：代码、自动验收、必要人工验收和双文档记录都完成。
- `进行中`：本轮唯一允许实施的步骤。
- `可开始`：依赖满足，但尚未开始。
- `未开始`：已经排入路线，但前置依赖尚未满足。
- `等待条件`：代码不能靠继续编写推进，需要真实数据、用户选择、账号或外部状态。
- `待讨论`：只有方向，没有得到足够明确的实施边界。
- `暂缓`：可做但优先级较低，不阻塞主线。

### 2. 每一步完成时必须同时写两处

1. 在 `共同协作.md` 顶部追加：完成内容、改动范围、自动/人工验收、未完成项和唯一下一步。
2. 在本文件对应步骤下追加：完成日期、提交号、验收文档、状态变化和顺序是否受影响。

缺少任意一处记录，就不能把步骤标为 `已完成`。

### 3. 新增或修改要求的处理流程

1. 先写入“需求变更记录”，标注是新增、修改、取消还是恢复旧要求。
2. 评估依赖、风险、成本、可回退性，以及是否会破坏已验收部分。
3. 需要改变顺序时，在“顺序调整记录”里同时保留旧位置、新位置和理由。
4. 重排后只开始排在最前面的一个 `可开始` 步骤。
5. 不因新想法直接并行开工；紧急修复除外，但也必须补记原因。

### 4. 临近阶段结束提醒

出现以下任一情况时，Agent 必须明确提醒用户“本阶段快结束了，可以继续讨论新内容”：

- 当前阶段只剩一个可执行步骤；
- 剩余项全部是 `等待条件` 或 `待讨论`；
- 下一阶段涉及账号、云服务器、付费服务、数据库迁移、外部发言或设备控制。

提醒只用于讨论和排期，不代表自动获得实施或外部操作授权。

## 五、顺序调整记录

### 调整 I：选B后细分S-15（2026-10-25）

- 原位置：S-14选择 → 单个S-15迁移/双读/备份/回退 → S-16。

- 理由：这些模块有直接文件读写、删除/抑制及private语义，不能把原文归档或单次导出视为全部迁移完成；先固定无损字段，再按依赖适配，最后演练一致备份与回退。
- 授权与范围：用户明确“选b，开始第一步”；本轮仅A，保留旧推荐作为历史。详细步骤见`方案-SQLite分步迁移-S15-2026-10-25.md`，无新增记忆能力，不提前部署或迁移正式数据。

### 调整 A：手机 GUI Agent 后移

- 原位置：渠道层之后、服务器之前。
- 新位置：服务器、QQ 和主动分享最小闭环之后，作为独立设备控制支线。
- 理由：用户的首要目标已经明确为“电脑关机仍能聊天和主动分享”；手机 GUI Agent 风险更高，且不是该目标的前置依赖。

### 调整 B：服务器不直接从 SQLite 开始

- 原写法：服务器先跑 Node Agent + SQLite。
- 新顺序：先在本机建立渠道抽象并用安全适配器跑通，再做无界面核心拆分；数据存储迁移单独设置决策门。
- 理由：当前正式记忆以 JSON/JSONL 为权威，尚无 SQLite 实现。直接迁移会同时改变运行环境、存储和渠道，失败时难以定位，也增加私人数据风险。

### 调整 C：真实关系和聚类验收改为条件检查点

- 原位置：记忆阶段必须连续完成后才能进入下一阶段。
- 新位置：保留为自动观察的条件检查点，不再阻塞其他主线讨论。
- 理由：正式关系为 0、聚类候选为 0；继续写代码不能制造真实语义证据，也不允许伪造私人记忆。

### 调整 D：私密记忆层提前到主动内容之前讨论

- 原位置：夜间调研中的“可照搬”灵感，没有正式排期。
- 新位置：渠道基础可独立先做，但在主动刷视频、两本日记或向外发送内容前必须完成设计决定。
- 理由：它影响哪些记忆可以发给用户、哪些只供 Agent 自己使用，属于输出边界，不应事后补丁式加入。

2026-10-24 更新：用户已批准第一版边界，因此把 M-30 整体放在渠道层之前；先做数据契约和统一过滤，
再做写入策略与本机查看。未批准的“对用户绝对不可见”不进入方案，因为文件位于用户自己的设备上，
只能实现默认隐藏，不能伪装成技术上无法查看。
