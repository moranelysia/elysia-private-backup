# 工具能力 T0 盘点与失败基线

日期：2026-10-15  
范围：只盘点当前开发版，不修改工具行为，不接入新服务。  
结论：当前登记表中共有 9 个工具。权限边界和基础错误处理已有不少测试，但“执行成功”“结果可靠”
和“用户目标完成”仍被同一个 `好` 布尔值混在一起。这是天气查出无关网页仍被当成成功的根因，也是
下一步 T1 必须先处理的系统问题。

## 1. 当前能力边界

- 已登记：`查 / 读 / 列 / 找 / 写 / 交付 / 跑 / 派 / 任务`。
- 没有登记真正的浏览器控制工具。`查` 是直接抓 Bing HTML，不会打开、操作或核对浏览器页面。
- 没有登记 DSH、Codex 或其他外部编码 Agent 工具。`派` 是项目内部的 DeepSeek 小助手，仍只调用
  同一张工具表。
- 工具调用由模型输出方括号标记触发，每轮最多并行执行 3 个，主循环最多转 3 轮。
- 工具记录界面只保留“成功/失败”布尔值和截短摘要；验证状态、来源、截断、重试、退出码和目标
  是否完成都会丢失。

## 3. 跨工具的系统性问题

1. **单一布尔值承载了三层含义。** `好:true` 可能只代表网络返回、文件能读、系统调用完成、
   进程退出码为零，主循环却把它当成“真的动过手并成功”。目前只要任何一项工具返回成功，完成
   闸门就会放行，无法判断用户真正要的目标是否完成。
2. **不完整结果没有统一表达。** 读文件裁中间、找文件达到上限、命令输出截断、子代理纸条截断、
   搜索只拿摘要，最终都没有进入同一个可判断的“部分结果”状态。
3. **取消链路不完整。** 主命令路径能取消，但联网搜索不接用户信号；主循环“打回重做”的工具
   调用和子代理内部工具调用也没有继续传 `中止`。用户按停止时，某些后台动作仍可能跑完。
4. **并行默认缺少依赖判断。** 同轮最多 3 个工具无条件 `Promise.all`。两次写同一文件、先写后跑、
   先生成后交付这类有顺序的动作可能竞态。
5. **模型承担了最后的真实性判断。** 工具原文交回模型后，由模型自己总结；子代理的最终纸条也由
   模型生成。程序没有把结论逐项绑定到证据，因此自然语言可能把部分成功说成全部完成。
6. **界面记录丢失诊断信息。** 当前只显示工具名、参数、成功布尔和 360 字摘要，无法区分拒绝、
   超时、取消、部分完成、未验证或结果不可靠，也看不到退出码、来源和重试次数。
7. **测试可出现假绿。** 本次 `测动手.cjs` 明确打印“工作区里的共同经历”未放行、统计 6/7，
   但脚本仍以退出码 0 结束。外层批量测试会把它记为通过。该问题应在 T1 同时修正测试闸门。

## 5. T1 建议的统一回执

T1 不需要一次重写所有工具。先在工具表外增加兼容归一层，旧工具仍可返回原对象，由归一层补成：

```js
{
  执行状态: '成功 | 失败 | 拒绝 | 超时 | 取消',
  验证状态: '已验证 | 部分验证 | 未验证 | 不适用',
  目标完成: '是 | 部分 | 否 | 未知',
  时间: 'ISO 时间',
  摘要: '给界面和模型看的短说明',
  证据: [{ 类型, 目标, 说明, 来源, 时间 }],
  来源: [],
  可重试: true,
  重试次数: 0,
  截断: { 有: false, 原始量: 0, 保留量: 0 },
  错误: { 类别: '', 说明: '' },
  兼容: { 好: true }
}
```

完成闸门应按用户目标需要的证据判断，不能再用“任一工具 `.好`”放行。T1 第一批只改归一层、
工具记录和完成闸门，并用 S01、F03、C01、A01、T01 验证；具体的搜索来源规则、写后重读和命令
产物检查留到 T2 分工具实现。

## 7. T1 完成状态与下一步边界

T1 已于 2026-10-15 完成：`脑/工具回执.cjs` 提供兼容归一层，主循环完成闸门、工作索引、近期
工具记录和子代理均已接入。五个最小回归样本 S01、F03、C01、A01、T01 已固定；旧工具仍保留
原返回字段，不需要一次重写。写、交付和学习任务可依据现有本地对象形成完成证据；查、读、列、
找、跑和派默认只证明执行或拿到材料，单独出现时工作状态保持部分完成，直到 T2 加入对应后验。

下一步是 T2：分工具验证与有界恢复。优先顺序为联网搜索、写入/交付、命令产物、读取/查找完整性、
子代理证据链。T2 开始前先给用户选择联网入口，不在本步擅自接入搜索 API、天气 API、浏览器自动化
或外部编码 Agent。联网入口仍按费用、授权、稳定性、来源覆盖、限流和迁移成本单独比较。
