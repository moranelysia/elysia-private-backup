# S-13：JSON/JSONL 与 SQLite 存储方案比较

日期：2026-10-25；源码基线`7f34740`。本步只读源码、配置路径字段和文件元数据，核对官方文档；未加载业务模块、读取正式记忆正文、运行数据库、改格式或安装依赖。S-14决定前不实施迁移。

## 建议

建议第一版上云选择A：保留JSON/JSONL，先统一单写入口、明确可恢复的写入状态、补齐一致备份和恢复验收。当前数据体量很小，数据库不是上云前置条件；先解决备份遗漏和桌面/服务单一权威，收益更直接。

如果你的优先级是尽早获得跨表事务、结构化查询和后续长期维护，可以选择B：在上云前迁移SQLite，但要接受更多改造与回退验证。它能简化同库数据一致性；不会自动改善记忆理解、模型口吻、关系推理，也不能替代单一核心或外发权限。

此建议是结合当前源码和规模的工程判断，不是性能实测结论，也不意味着已经替用户选定A。

## 两个可选方案

| 比较项 | A：保留JSON/JSONL并加固（推荐） | B：迁移SQLite |
|---|---|---|
| 当前数据迁移 | 不转换正文，保留旧格式；建立清单、版本与写入口 | 设计schema和适配层，导入验证后切换；原JSON只读留档 |
| 一致性 | 单写队列+单文件替换；跨文件操作要记录阶段并幂等续做 | 同库多表可事务提交，减少临时晋升等中间状态 |
| 查询 | 目前简单，日志增长时要分页/分段或索引 | 按会话、时间、类别建索引，查询能力更完整；索引也需设计 |
| 并发 | 所有持久写入必须收敛到同一核心；普通旧文件入口不能各自写 | 写操作仍需协调、处理忙等待；不把SQLite当跨机器共享盘 |
| 运行与资源 | 无新数据库运行组件，沿用Node；内存/延迟仍要实测 | SQLite可嵌入服务，无需另租数据库服务器；驱动/缓存/线程及版本待验证 |
| 备份 | 暂停接收、排空写入，复制同一代文件+清单；不靠随手拷目录 | 用数据库备份接口取得一致快照，再配套附件及版本清单 |
| 回退 | 版本不变时较简单；仍须隔离恢复、校验和防双写 | 切换前可退旧快照；已有新数据后必须逆向导出并核对，不能直接启用陈旧JSON |
| 日常查看 | 文本便于查阅；正常人工修改仍优先用已有界面 | 需专用查看/导出工具；保留UI和JSON导出以便检查 |
| 同步 | 文件可比对，但多端写冲突不会自动消失 | 单库不自动解决离线合并；变更序号、版本与删除标记仍由应用定义 |
| 开发量（粗估） | 约2–4个工程人日，主要补写入/备份/恢复；非工期承诺 | 约7–12个工程人日，含数据适配、迁移、逆向回退和回归；非工期承诺 |
| 主要代价 | 长期维护恢复协议；文件增长后要重新评估 | 现在改动面大；迁移漏字段、驱动兼容和回退是主要工作 |

估算是本项目新增存储工作的相对量级，不是已测工时、不对应Plus额度；S-16/S-17的常驻运维与Linux资源验收是两方案共同的后续工作。没有下载/安装数据库或依赖来支撑此比较，未测量数据库占用，不能承诺换库节省多少内存或费用。

SQLite的事务可解决同库修改的一致性，但附件文件、模型请求与外部发送不在该事务内。[官方原子提交说明](https://www.sqlite.org/atomiccommit.html)；它适合嵌入式本地存储，无需单独数据库服务。[适用场景](https://www.sqlite.org/whentouse.html)

WAL支持读写并行但同一时刻仍只有一个写者，要求同一主机；活动WAL属于持久状态，不能随意只拷主db文件。[WAL说明](https://www.sqlite.org/wal.html) 活库快照可使用Online Backup API。[备份接口](https://www.sqlite.org/backup.html)

当前命令行Node为v26.8.2，对应内置`node:sqlite`仍标release candidate，DatabaseSync为同步API；没有核对Electron内置Node与目标Linux驱动，不能视作已解决兼容或UI阻塞。[固定版本Node文档](https://nodejs.org/download/release/v26.8.2/docs/api/sqlite.html) 若选B，优先在独立核心确认受支持版本和执行线程；WAL候选还须核对是否包含官方2026年WAL-reset修复。[版本要求](https://www.sqlite.org/wal.html)

## 共同前提：单一权威与一致备份

桌面和服务器最终访问同一个核心。不能让本机、手机和服务器各自直接修改一份文件或同一个网络共享数据库；离线多端合并不是当前两方案的默认能力。JSON或SQLite都保留内部对话编号、来源消息归属、版本及删除标记，后续同步走受控接口。

S-15/S-16必须区分：正式记忆/日记/附件与人工删除标记、渠道映射/去重/待发状态、待提取缓冲属于必须恢复的业务数据；关系图布局属于应单独保留的偏好；下载缓存/实验产物不默认复制上云。凭据单独管理，不混入源码、普通报告或记忆导出。旧Git源码备份不能替代业务一致快照。

备份清单应记录源码提交、数据格式/规则版本、文件字节数/哈希、截点时间和附件清单；私密日记备份与面向用户的shared导出分开。恢复只写新目录，校验后切换；禁止直接覆盖运行中的正式目录。数据库方案同样需要附件/私密边界与恢复演练。

## S-14选择后怎样实施

选择A时，S-15先制定并隔离验证存储清单和适配边界，保留JSON/JSONL；识别所有写者、补关键坏档拒写和持久状态回执，不批量重排/改写历史。S-16再补一致备份、停止/排空/残锁接管、故障恢复及单写总入口。若需跨文件强事务，不能只把rename/fsync称为已经实现。

选择B时，S-15先在虚构样本上验证schema：会话/消息、事实/经历/小本子、临时生命周期/评估证据/晋升、关系/自动抑制、日记/删除标记、渠道映射/任务/用量，另留原始扩展字段；不将附件大文件塞进数据库。保留稳定ID、原时间与未知值、可见性和人工修改，不猜旧时区。影子库只核对，不双向产生新记忆；截点停写、只读导入、逐类比对通过后才切权威。切换后的回退要先停止新写、导出新增与删除差异，验证旧格式可完整恢复；失败继续维持已验证的权威库，不能静默丢新数据。正式数据的实际切换仍留S-23。

两种方案均不得修改自主晋升门槛、记忆叙述/private规则或启用M-22/M-23；存储改造不是新增记忆能力。选B也不把当前459项回归直接算成SQLite验收，须另做事务/崩溃/导入导出与删除恢复验证。

## 什么时候重新评估A

出现以下任一项即可重新比较，不必等数据达到某个大小：跨文件失败恢复频繁、查询明显依赖多条件关联、要求同库多表事务，或在目标环境测得本地历史读取/筛选持续超出约定延迟目标。当前64MiB历史读取保护上限前必须评估分页/分段/迁移，不能到上限才处理；大小不是唯一决策依据。

目前推荐A，主要依据是体量小、既有隔离回归与可恢复逻辑可复用、先跑通个人自用部署的目标。若你愿意现在投入额外改造换取事务基础，B同样合理。等待S-14明确选择，本轮不自动实施任何一个方案。
